## Trial 1: masked output multiplication

For each input w, take preprocessing masks A_w in F2^m, V_w in F2 and T_w=A_w V_w. Mask the secret operand and source operand by opening
    D_w=S+A_w,
    E_w=b+V_w.
The usual product reconstruction is
    Z_w(E)=T_w+D_w V_w+E A_w+E D_w
          = (D_w+A_w)(V_w+E)
          = S (V_w+E).
For E=E_w this is S if w is qualifying and zero otherwise. This is exact for all witnesses and arbitrary mask distributions; no KDF collision, native/source proof equality or proximity assumption. An alternative return encoding would add a publicly known sentinel to the zero output; its difference between the two possible openings is unchanged. The intended offline compiler would publish public preprocessing from which anyone can construct the masked transcript using the full source certificate. Bitcoin would still see only the native signature.

Try to generate a fresh D_w without revealing A_w or keeping an online party. Build chooses public seed d and defines D_w=H_expand("D",x,d,enc(w)); define A_w=S+D_w privately, which Build can compute for any supplied w. This defines the required correlation without publishing the secret mask or separately enumerating each D_w; from the seed alone the public D_w has no S dependence. Next sample a public seed v and set V_w to the first bit of H("V",x,v,enc(w)). These seeds can be erased locally after publication. E_w is now publicly computable from the full R_x and V_w. The exact multiplication can be regrouped into
    U_w=T_w+D_w V_w=S V_w,
    Z_w(E)=U_w+E S.
Here the simple preprocessing generation of D_w succeeds but the correction does not: if the public preprocessing exposes U_w for any index with V_w=1, it exposes S. If V_w=0, U_w=0 and the E=1 correction is S itself. Publishing both encrypted multiplication rows with a publicly computable row key does not improve this.

## Trial 2: secret V_w, opaque jointly correlated preprocessing

Try to hide V_w rather than use the public seed. Allow a hypothetical public expander which returns the masked operand opening E_w and a public reconstruction interface Eval(C,w,E). To favor this repair, let masks be secret, arbitrary nonlinear functions of all of w, and never provide an attacker with A_w, T_w, private coefficients, or any label for a different input. The proposed Eval has the ordinary masked-product correctness equation above on both supplied E values for the *same* w and preprocessing. Only the full-verifier-produced E_w is used by honest Open.

This interface has an exact straight-line attack. Choose a canonical syntactically representable but invalid original certificate w0 (the relation has such inputs). Compute its public masked opening e0 and invoke the same reconstruction interface at e0 and e0+1, reusing w0 and its preprocessing. If honest code rejects before opening, this attack applies when the masked operand and the two-row interface are separately public computations on that index, as in this trial; it does not assume the ability to bypass a genuinely cryptographically gated interface. Then
    Eval(C,w0,e0)+Eval(C,w0,e0+1)=S.
In fact Eval(C,w0,e0+1)=S because b=0 for w0. Both invocations use the identical complete input index, not two incompatible source histories or different preprocessing triples. The attack neither learns a hidden mask nor solves R_x on a true input. It applies also if the public row interface is supplied as opaque callable functionality rather than exposing its internals. Correctness on both row openings with negligible error gives the same attack with error at most the sum of the two errors. If the preprocessing were freshly randomized at each call but the transcript and its two row corrections were publicly reproducible from the sampled tape, fix that tape for the two invocations. Arbitrary coherent attacks are not needed: this classical attacker is also a valid QPT attacker. No claim is made that this proves insecurity of every source-dependent evaluator; it rejects this exact reusable masked multiplication interface.

The differential is the native secret itself, so arbitrary high-degree or domain-separated hash derivation of A_w,V_w across distinct w does not help. This is not the low-degree extraction of R327: the attacker uses two row openings at a SINGLE index and the linearity is in the one-bit multiplication selector inherent in this particular product, not in the source trace or source masks. Nor does an independent native signature checking key repair the attack; it merely checks the result.

## Trial 3: authenticate the operand opening with a full-trace commitment

To avoid permitting the alternate opening at the same index, try to bind E to a hash commitment or MAC of the entire source trace. The intended serialized local row corrections are encrypted under per-index keys, with domain and associated data including (x, enc(w), E), not reusable occurrence labels. More explicitly, attempt a public row ciphertext expander returning
    C_E(w)=Z_w(E)+H_expand("row",x,s,H("trace",x,enc(w)),E),
where s is a public independent seed and enc(w) covers the whole original certificate. Open computes the full trace commitment, E_w and its row key, verifies the trace proof or MAC tag, and unmasks the row. Both full certificates and both opening values are separated in the hash domain, so the attack is not a literal ciphertext replay.

If the expander has the stated public two-row functionality, then the alternate row can still be decrypted: the attacker computes the alternate E and its hash key and bypasses an ordinary public check of the trace-proof/tag. A publicly recomputable tag or hash of a transcript authenticates no hidden row key. Even if a proof system prevents obtaining an accepting tag for the false opening, a tag checked only by ordinary software before decryption has no cryptographic effect on these public row keys. This is an exact failure of the proposed serialization, not an attack on proof soundness.

Repair by including the *accepting proof bytes themselves* in the KDF, and requiring that the row ciphertext can only be computed using those bytes. This does make a forged alternate opening unavailable if the proof is sound and the resulting encryption is actually bound to the accepting proof bytes. But it also changes Build: it now needs to generate public correction data for every future accepted full-proof byte string, none known at setup. A public independent mask of such bytes allows any caller to remove it, including from an unchecked false-row ciphertext. Precomputing ciphertexts for individual acceptable proof strings requires enumerating the strings (no such polynomial enumeration for the full original relation is supplied). Generating a ciphertext by public software that first checks the proof and then returns the secret-dependent row requires the very source-gated secret computation being sought. The same applies to a hidden MAC key: a public verification tag does not produce the encryption key, and a retained online MAC issuer is not permitted. A putative compact expander with a cryptographic restriction to the unique correct row would be a materially different primitive, and would have to be built and jointly simulated from hashes, not assumed.

A more targeted repair would let V_w depend on b itself, e.g. V_w=b+H("e",x,w)_1, so E_w is a public hash bit independently of the predicate. This merely moves the necessary source dependence to U_w=S V_w and the final row correction. The public hash bit alone cannot determine the hidden product. If the ordinary two-row reconstruction survives, the same-index differential survives unchanged. No alternate row-key or MAC-tag placement sweep is justified.

## Simulation and composition screen

All attacks above use only the specified public interfaces and their classical outputs. They do not rely on extraction from an adversary's query log, a representation supplied by the adversary, auxiliary knowledge of source coins, or correlation between unrelated capsules. They already violate unauthorized exact-signature recovery in a single honest capsule. Thus adding source auxiliary information, selective openings, related capsules or malicious setup to the security game cannot salvage these instances of the trial. The equations are algebraic and do not purport to justify a QROM programmed-oracle transition or a concrete hash reduction. Conversely no inference is made that an independently secure, source-bound row expander is impossible, or that a fully public representation of a secure circuit must expose the hypothetical Eval interface in Trial 2.

Handoff: the next construction must avoid exposing both masked output rows at any fixed input, even if the full trace is used to derive fresh preprocessing. For this direction the missing equation is a classical PPT serialized one-sided row compiler, with ciphertext and key correlation generated without knowing future qualifying proofs, where only correct original-certificate-controlled reconstruction exists in the full public view, rather than an ordinary product gate with a software authentication check. A general proof of validity, one-time MPC privacy or simulator of a single honestly selected multiplication row is not that compiler.
