## WOTS+ double-vote native-spend adapter and exact failure
Model a single WOTS+ one-time signer using base 16. A signature on message m discloses chain value `F^(d_i(m))(sk_i)` at each base-16 message+checksum digit i. Two signatures for m0 and m1 allow public forward hashing to the same key's target signature chain value at digit d_i(m_cancel) only if

    for EVERY i: d_i(m_cancel) >= min(d_i(m0),d_i(m1)).             (E2C-1)

Within this one-way-chain interface the condition is necessary and sufficient for *forward-only derivation* of a third WOTS signature; outside the interface a chain-inversion break would be needed for a smaller target digit. For every fixed target whose digit at i is below 15, there exist distinct signed source digests with both observed digits greater than the target. Such a pair cannot sign the frozen native cancellation through forward hashing. The protocol provides no guarantee that qualified source digests satisfy (E2C-1), so every-witness completeness fails. Different signers' WOTS parts do not assemble into an ordinary native signature under one verification key. No implication to actual SLH native forgery is asserted.

High-digit target-message grinding cannot be silently substituted: WOTS checksum adds restrictive low digits; a message forgeable using two votes may be forgeable with only *one* normal vote, causing early unsafe cancellation; an unknown-future dependent target cannot be fixed at Build. Binding a source equivocation receipt in a new Bitcoin script instead would violate the ordinary-native-cancellation-signature endpoint and would not cover the independently usable original work/burn/AuxPoW branches. Nor does a separate public source verifier after key leakage repair secrecy.
