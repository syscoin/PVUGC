## 1. State and actual serialization

Let V_x be the complete original relation with all three independent grounds. Grant a deterministic bounded circuit evaluation or sequential verifier trace A_j(w), j=0,...,T, with w retained in the state, each transition T_j checked against the complete preceding state, and acceptance exactly V_x(w). This grant concerns semantics, not access to hidden bits.

Define d_j = H_state(ctx,j,encode(w,A_j(w)),d_(j-1)), with initial d_-1 fixed by ctx and injective encodings. ctx binds original statement, claim, chain, slot, exact native message and key, and capsule ID. Let S be a hash-only signature system (for the diagnostics grant perfect correctness and ordinary unforgeability when its secret key is not disclosed). The target certificate on a transition is a signature on

    m_j = encode(ctx,j,d_(j-1),d_j,pk_(j+1,d_j)).

A verifying state record includes w, the preceding certificate, the next public key, and the signature. The complete digest and predecessor-dependent message are deliberately included, not just the local gate row; signatures from unrelated states cannot be substituted by literal equality of the signed message. An ideal restricted delegation would authorize a next key/signature only on the consistent T_j step. The final state would still need a cryptographic release of sigma_cancel for acceptance, not merely a public verification check.

Try a concrete static serialization: Build samples per-stage independent signing keys sk_j, publishes pk_j with a root signature covering the ordered stage keys and context, and supplies public evaluation descriptors to generate each transition signature. This is polynomial and needs no witness. It avoids storing a separate public key for every possible state, and the signatures, if correctly generated, cover the exact full digest. However a descriptor containing sk_j, or a seed with which public evaluation reconstructs it, permits signing every m_j under pk_j. An honest-code check of the previous certificate or T_j before signing is not a restriction on the serialized secret. The entire earlier-state binding is then authenticated by an adversary-controlled signing operation. This failure is independent of whether the actual source verifier is computationally hard to satisfy.

The repair under examination is to avoid ANY reusable sk_j by deriving unique keys from a hidden setup seed for each complete digest:

    s_(j,d) = H_seed(ctx,j,d,s_root)
    (sk_(j,d),pk_(j,d)) = KeyGen(s_(j,d)).

Treat H_seed as an independent hash domain in the diagnostic; KeyGen is deterministic on its explicit coins. A child key is authorized by a signature under the current key on m_j. A certificate at state d cannot simply be normalized to another namespace. This is different from a static stage key or a row-root seed exposed by the previous transport proposal. Build can compute the key for any particular chosen state, but has no future qualifying w. A serialized public descriptor must enable both the child-key authorization and the necessary next signing operation without exposing a universal signing authority.

## 2. Dynamic delegation equation

If Open can derive s_(j,d) from public seed material for ANY d, then all corresponding sk_(j,d) are likewise public. Adding a root-signed list of *stage identities* does not authorize only consistent state transitions. An attacker holding a certified current key can sign m_j for an arbitrary d_j and any child public key, including one for which it knows the secret. This is a direct substitution at the exact next-key authorization, not a collision of the full-state digest or a mixed garbled wire label. In particular it works even if H_state is an ideal collision-free commitment for all queried states.

If the public keys are instead fixed by a public rule PK(ctx,j,d), and the verifier rejects an arbitrary child pk, the signing descriptor still must yield the corresponding sk for the actual d. If it can do that for arbitrary d, the illegal-digest choice has not been constrained. If it only does that on original-consistent traces, the missing operation is a source-conditioned seed/secret evaluator. Calling KeyGen with a digest as public randomness is the first, insecure case. Calling KeyGen with secret setup randomness and claiming that a certificate makes that randomness available is the latter, unimplemented case.

One could pre-sign child authorizations in Build, thereby avoiding disclosure of the current signing key. This is a genuine secure local transition allowlist for a finite, explicitly enumerated state space. For each allowed digest and successor, serialize an ordinary signature over the full m_j plus the next key material (or an independently restricted next descriptor). It authenticates exactly those pre-signed messages, subject to the signature assumption. A Merkle commitment to the same allowlist gives the same authorization after a valid leaf opening. But the state includes the complete canonical future w, so a fixed finite explicit list covers only those distinct messages actually in the list. For fresh state d outside the list, Open needs an unlisted signature; ordinary EUF security forbids generating it from the pre-signed list alone without an additional trapdoor or a break. This is a correctness preflight in the case where the relevant witness produces an unlisted message; it is not a count or lower bound on the number of actual Syscoin/BTC histories or a universal black-box impossibility. A Merkle root is a commitment to the explicit messages, not an algorithm for generating authorization leaves for unlisted messages.

The same issue appears if the parent signature only covers a reusable template (ctx,j,row,pk_next) and Open appends d_(j-1),d_j and a public hash of that tuple with the template signature. Anyone with that template signature can append different digests and recompute the public hash. The signed message is unchanged; the appended digest is not signed. This repair cannot use signature unforgeability to infer full-state binding. Do not replace the missing restriction with a proof-carrying public transition: a publicly verifiable source/trace proof can establish semantic validity, but it does not cause an otherwise inaccessible signing secret or fixed native capability to become available.

## 3. Restricted hash-chain authorization repair

Consider an actual hash-only partial-signing descriptor rather than a raw sk. Use independent forward hash chains for the digits of a message encoding a in base B, with the usual checksum appended, signature components H_i^(a_i)(s_i) and public verification endpoints H_i^(B-1)(s_i). A descriptor containing one component at exponent r_i in every chain can produce signatures at digit vectors satisfying a_i >= r_i for every i, by public forward hashing. This is a concrete nontrivial restriction, and it avoids handing out all chain roots if some r_i are positive. This is only a forward-evaluation property; no converse for arbitrary QPT attackers is asserted.

If the descriptor for a transition is made by providing the components of several permitted messages under the SAME key, all their components are public. The union provides the coordinatewise minimum r_i across those messages; thus it enables every valid message encoding dominating r coordinatewise, whether or not the message was permitted. This remains an issue with the checksum. Exact base-2 example at the already-encoded message digit level: four data digits 0011 and 1100 both have complement-sum checksum 2, hence identical three checksum digits 010. The disclosed components give all four data-chain starts and the common checksum components. They produce a signature at 0101 with the same checksum, using only public forward hashing. The new data vector is not one of the two authorized vectors. This is a functional example at the message encoding level, not a claim about finding actual full-state digests with those particular digits or forging an actual SLH signature. Hashing whole messages before encoding would add a digest-preimage constraint; it would not establish exact original-transition authorization for arbitrary sets of digests.

The explicit repair of using an independent key for EVERY complete state and allowed outgoing transition prevents this same-key component mixing. It returns to the dynamic certification equation in section 2: the honest Build must certify the independent key and enable the right restricted signing descriptor for the future state without knowing it. Publishing a reusable parent signing secret undoes the repair; pre-signing every relevant independent key is an explicit allowlist, not a practical source verifier compiler. Therefore do not implement larger multi-use OTS fixtures, vary WOTS bases, or invoke a generic constrained signer that already has the missing source-conditioned key access property.

## 4. Terminal equation and joint simulation

Even granting an ideal verified sequence of state certificates, the complete original witness-dependent certificate transcript tau(w) varies across qualifying w. A public mask E=sigma_cancel XOR H_final(ctx,tau(w0)) generated from a chosen transcript tau(w0) does not open with every other transcript. For distinct fresh inputs in an independent final hash domain the outputs are independent uniform, so one shared mask has no guaranteed equality. This is not an assertion that every actual source transcript is unpredictable or that all possible correlated final functions fail. A fixed terminal signing key supplying the SAME native capability would avoid that equality equation only if access to its secret/authorization were truly cryptographically source-conditioned. Releasing that secret after a public proof check in ordinary public code is not such an access mechanism.

The simulator must account for actual dynamic key correlations, root authorizations, public partial chains, exact native endpoint and auxiliary/sibling data. Replacing genuine pre-signed state messages by unrelated simulated ones breaks honest verification on a supplied qualifying witness. Publishing all state-key seeds makes signatures independently computable, not evidence of original-consistent evaluation. Neither is a simulator for a secure capsule.

Next required operation if retaining certification: concrete serialized source-restricted delegation of new full-state signing authority without handing an unrestricted signing key to public evaluation, jointly with a fixed native terminal release rather than variable transcript hash. This would need an actual new hash-only correlation, not an assumed restricted signer or online certificate issuer. Prefer a route avoiding delegated signing altogether if it cannot instantiate that operation. No claim about impossibility of source-specific computational hash release in general.
