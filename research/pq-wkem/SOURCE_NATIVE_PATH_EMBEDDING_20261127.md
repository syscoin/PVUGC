## Selection before implementation

Missing operation: Build(x,S) must serialize a capsule for a fixed native cancellation capability S, opened by EVERY qualifying ORIGINAL w for the complete R_x(w). Keep the three original OR grounds, their authentic admission, maturity, relevance and all claim/native-message bindings. R_x is an abstract reference to that full bounded verifier, not a newly implemented compiler.

Instead of publishing a separate encrypted output, try embedding a source authentication path directly into a one-way hash path that is already part of the frozen native verification computation. The mathematical change is to share a commitment between the source and the native output path, rather than evaluate a private source coefficient, construct independent garbled input labels or ask a witness to compute the prior MPC mask. In particular, investigate whether DIFFERENT source paths can converge to the SAME fixed native signature component without Build knowing the future witness. This is a candidate source-to-capability coupling, not a native signature-size optimization. It deliberately grants favorable hash-path alignment in order to test whether alignment itself would provide the necessary common output. Do not assume actual Bitcoin/Syscoin and SLH hash domains or tree layouts align.

## 1. One-way chain embedding

Work first with one synthetic n-bit component p of a fixed native capability. Grant a native verification chain with public, individually domain-separated functions F_i: {0,1}^n -> {0,1}^n, i=0,...,L-1, and a fixed message-dependent signature position d. Write F_[a,b) for their ordered composition; F_[a,a) is the identity. The public endpoint is z_L. Verification accepts p at slot d when F_[d,L)(p)=z_L. This isolates a WOTS-like verification chain; it is NOT an implementation of SLH-DSA, nor a claim that the actual signature verifier has an independently replaceable chain. Assume collision binding of the relevant F_i when using binding arguments. Build knows p and can compute its entire forward suffix z_j=F_[d,j)(p), j>=d. Grant all remaining native signature material and verification structure fixed and available, so the only unresolved release in this trial is p.

Try sharing an externally authenticated source commitment A with some native position a. The intended actual honest computation is:

    Build(p): compute z_d=p, z_{d+1},...,z_L;
              publish endpoint z_L, shared source anchor A=z_a, and context.
    Open(w): obtain (b,v) from the authenticated ORIGINAL certificate;
             require R_x(w)=1 and F_[b,a)(v)=A;
             return F_[b,d)(v), for b<=d<=a.

This is a concrete polynomial chain algorithm for the stated alignment premise. An ordinary honest-code R_x check is NOT credited with secrecy. In particular, for an independently supplied source A, Build must actually check A=z_a; it cannot claim authority to replace a consensus-authenticated commitment by its own z_a. If a=d, p=A is public. If a<d and there is an aligned public value at that position, the native chain computes p from it. Thus an anchor at or before the signature position cannot act as a secret input. The only potentially useful placement is a>d.

For a>d, any honest w providing the advertised v at b<=d yields p'=F_[b,d)(v) with F_[d,a)(p')=A=F_[d,a)(p). If p' differs from p, define the first k>d at which the two forward values agree (there is one by a). The distinct inputs at k-1 collide under the SAME F_{k-1}. This is a deterministic reduction with no rewind. Consequently the collision-free executions give a common component even for different b and different v; no requirement that the entire source witness be identical. This is stronger than simply hashing two proof strings and expecting their pads to agree, but only applies to the exact chain-alignment premise.

The actual missing operation is now exposed: R_x(w) supplies no stipulated path from a witness-dependent point at b<=d to this independent native anchor A. It checks the original source history/evidence, not the above native chain. To use a fixed original source anchor as A, Build has to arrange its native chain suffix to hit that anchor while possessing the frozen p, and the opener must supply a path that starts before the secret slot. Choosing a native chain from p does not generate a new authentic source anchor. Choosing a public actual source anchor as the chain start produces an entirely public suffix and does not hide p. The known public anchor and the chain endpoint alone do not supply the missing earlier node to an original witness. A native hash chain has fixed unary transition functions; a source path can depend on sibling hashes, header fields and other witness-dependent data. Those cannot simply be extra inputs to F_i without changing the native verifier. Even if hash domains happened to align on one source step, no premise makes ALL original qualifying witnesses furnish an earlier node on the same chain.

The proposed chain construction is therefore rejected before coding: correctness for the actual full original relation has not been achieved. The chain-collision argument is not an arbitrary unauthorized-recovery reduction. In particular, an attacker who finds the exact p without any collision has not necessarily furnished original evidence. A collision reduction for two distinct accepted chain starts does not handle that event.

## 2. Repair attempt: use branching source authentication rather than unary native chains

The native-chain restriction suggests using the Merkle path part of a hash-based native signature instead. Try allowing different original source witnesses to authenticate different leaves and letting their paths merge at one shared hidden sibling. Work with an ordered binary tree hash G_i with explicit domain, height and direction; grant matching encoding and context to both sides for this trial only. Build knows an authentic pre-existing source root A, and the hidden native node p. Compute the outer commitment B=G(A,p). Publish A,B and the fixed placement of A on the left. The intended Open takes ANY complete original certificate with a path to A, verifies the original relation and that path, and extends the path by one right sibling to B. The last node p would be the exact fixed native contribution. Different leaves and inner paths are allowed; no shared inner witness preimage is assumed. This explicitly removes the restriction that every source authentication be a unary native chain.

There is a complete public algorithm for computing B, and a complete public algorithm for verifying the extended path GIVEN p. There is no algorithm to construct the extension from the original path alone. Specifically, folding the original inner path yields A; all of that computation is independent of p in this trial. The required last step is finding p such that G(A,p)=B. Publishing the extension supplies p outright, including on FALSE x. Publishing only a proof that the extension exists does not supply its missing node. Letting the path stop at B without supplying that sibling changes the native verification predicate.

For the exact ideal-hash synthetic trial, fix an original certificate w and A independently of uniform p, take the separated outer domain G, and expose B=G(A,p), plus the independent source data. A simulator of this partial public transcript can sample B uniformly and program the one point (A,p); this is the actual real distribution in the ideal model for this experiment. Before the first query to that point, p remains uniform among the unqueried n-bit candidates. Classical honest evaluation with q guesses has probability at most (q+1)/2^n of producing the exact p (including its final guess). An alternative right sibling authenticating the same B would require a distinct input to the same outer hash with equal output. This is not a claim about concrete SHA or arbitrary correlated native data. It identifies the independent-opening obstruction for this particular repaired transcript; possession of the original inner path does not give the hidden sibling. The repair is rejected before implementation rather than rerunning the already-recorded independent-opening tests.

Could instead embed p inside a tree that the SOURCE already authenticates, so that actual witness paths already carry p as a sibling. This differs from the overlay: a real inner source path containing p would actually provide the missing component. But a source tree pre-dates or is generated independently of the offline native setup. Build has neither authority to replace the tree root with B nor a premise that all the original independently sufficient grounds include one fixed hidden sibling of that tree. An ordinary source Merkle path may terminate at a different root, a different position, or be absent from a particular original ground. Merely appending B to public claim metadata does not cause the source to authenticate paths through B. Requiring future source certificates to carry a path through a setup-created tree is a new source condition, not the original relation. If all those paths can be generated from public tree material at setup, the missing sibling is also publicly obtainable. Do not replace this missing cryptographic coupling by a new source signer, online response or new consensus commitment.

## 3. Handoff

Direct native-path embedding would be a real release only with an executable joint source/native construction: Build must create the correct frozen native capability and checking data while every qualifying original witness independently supplies an authenticated earlier path to the SAME secret native node. The complete public transcript, including the native checking data, must make arbitrary recovery of that node or accepted forgery imply original evidence or an independently justified break. The collision-free common-output observation in section 1 and the explicit overlay in section 2 do not establish these requirements. Neither standard Merkle binding nor the ability to check a native hash-based signature proves them.

Do not retry another choice of chain length/position, source hash domain, or Merkle overlay sibling. A new candidate would require an actual source-driven joint commitment construction without changing source consensus or the native verifier; granting the original witnesses knowledge of a hidden native node is granting the desired operation.
