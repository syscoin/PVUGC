## Exact failure of the named Source-Bound Branch-Multiplexer

Partition source witnesses by polynomially many semantic slots j (challenge type, divergence height). Try one ciphertext row `E_j` per slot, and raw opening `K = E_j XOR F(context,w)` on a *complete source witness* w. If two different **valid** transcripts u,v share slot j, correctness for the same K requires `F(ctx,u)=F(ctx,v)`. Hence distinct hash outputs cannot open the same row; this is an algebraic identity, not an assumption about honest verification. Under a random-oracle F with κ-bit independent unqueried outputs, a row fitted to one accepted witness works for r accepted distinct unqueried witnesses with probability `2^(-κ(r-1))` when the remaining outputs are independent. This is a restriction on **this per-slot XOR-pad normal form** only. It is not an impossibility for hash-only WE, standard-model SHA or full coherent QPT attacks.

Replacing the witness-dependent pad by `F(ctx,j)` allows Setup to fit every source certificate but makes the pad PUBLIC, and `K=E_j XOR F(ctx,j)` leaks without any authenticated challenge. Supplying a secret source-issued pad is not implemented by current AuxPoW tags, fails retained-secret assumptions or adds an online issuer. Domain-separated SHA-256 synthetic checks: 9,216 assertions across 128 seeds, 8 slots and 3 distinct child outcomes; two different parent-work certificates for the same pure child are normalized as one outcome. No BTC/SYS best-chain qualification was tested.

**Polynomial interpolation repair tested:** A public polynomial P with P(z_i)=K for r distinct hash-encoded qualifying source outcomes has either public constant value P≡K (immediate exposure), or `degree(P) >= r` by the root bound for P(z)-K. Explicit `P(z)=K+a∏(z-z_i)` works on only the PREKNOWN source hashes and fails unforeseen original witnesses. Toy F_65537 checker: 12,300 assertions; not a PQ security experiment or an exhaustive theorem about non-polynomial representations. This is not an optimization proposal.

## Conditional constructive source-binding interface: own-input annex

A fixed-body activation transaction may have TWO known inputs. Input 0 spends a vault slot with already-made N-of-N signature(s) and **no annex on that input**. Input 1 spends a preallocated one-of-N notary authorization-token UTXO. At activation ONE notary chooses a short source claim digest `a`, puts it in **input 1's annex**, and signs input 1 with a sighash that commits to *its own annex* plus the fixed transaction body. Changing input 1's annex changes its signature digest but not input 0's; the N-of-N preauthorization stays valid, while the notary cannot silently substitute an unsigned assertion. All signed outputs/prevouts remain fixed, with no SIGHASH_NONE or open outputs.

The pinned `SignatureHashSchnorr` implementation hashes transaction-level data and **execdata.m_annex_hash for the CURRENT input only**, when `m_annex_present` (see `src/script/interpreter.cpp` pinned above); it does not commit to another input's witness annex. This supports the dependency design under pinned Schnorr/Tapscript semantics, NOT claims that an SLH/P2MR native PQ endpoint is deployed or has identical sighash rules. A native hash-based endpoint with analogous input-local annex semantics is a **conditional prerequisite**.

Bitcoin `txid` excludes the runtime witness/annex, so downstream preauthorized cancellation may spend the fixed activation txid. Bitcoin `wtxid` includes the annex; off-chain a complete witness inclusion proof through the coinbase witness commitment, coinbase inclusion against BTC header, plus qualified anchored BTC history, can bind the *actual activated assertion*. This is not a proof that an arbitrary privately mined BTC header is the winning chain. The annex carries only a short digest; original source evidence remains off chain. A preallocated authorization-token outpoint, actual one-of-N script path, fixed outputs, witness availability, reorg/anchor qualification and malleability-resistant signing are REQUIRED. A mere unused OP_DROP witness slot without the notary's signature binding it is malleable and UNSAFE. One token/slot is consumed, and unlimited later dynamic recipients/amounts are not supported by this fixed-body example.

Local code executed twice with byte-identical captured outputs: 840 SegWit witness-commitment byte-binding checks and 2,400 **symbolic** per-input HMAC/sighash isolation checks; real signatures, script execution and consensus validation were NOT run.
