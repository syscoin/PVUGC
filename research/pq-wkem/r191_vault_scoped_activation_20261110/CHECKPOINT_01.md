## Hypothesis

A technical conflict remains in the design: N-of-N participants have to preauthorize a fixed cancellation message M before funding, but a single notary may activate a withdrawal claim a only later. A claim-specific capsule with x_W(a) cannot be newly generated by the erased honest setup signer after a is chosen. A possible source-dependent *relational* repair is one vault-scoped frozen message M_v, with activation a supplied by the challenge witness and required to be authenticated as a spend/active claim of the same vault's fixed outpoint.

Define x_v=(vault outpoint, epoch, M_v, native VKs, anchored Bitcoin comparison policy, source chain/authorization policy, window/deadline, capsule ID). Define A_v(a,pi_A)=1 exactly when pi_A authenticates the *actual* qualifying activation of that vault/epoch according to the specified Bitcoin comparison/branch policy, with a containing the later full claim ID, burn/amount/recipient and source assertion.

Define R_v(x_v,(a,pi_A,j,w)) = A_v(a,pi_A) AND R_cancel(x_W(x_v,a),j,w), where j selects the three real challenges. x_W is computed and authenticated from x_v and a, not chosen ad hoc by an attacker. The signature M_v MUST spend a fixed outpoint to a fixed safe cancel/reset/refund destination independent of a. If cancellation spends a later variable outpoint or is signed with SIGHASH_ALL binding an unknown a, no such shortcut exists. It is a conditional graph compatibility check, not a claim about deployed native PQ or BitVM transaction templates.

### Precise functional claim to prove/test

Under a unique admissible activation a* for the fixed vault/epoch and a qualified complete source-authentication policy, R_v has the same admitted underlying fault language as R_cancel(x_W(x_v,a*),.), up to redundant valid activation-proof encodings. Authentication of a* is INSIDE R_v, not a public Boolean chosen by the adversary. Different anchored chains might contain conflicting vault spends; if those chains are simultaneously admissible, this is no longer a unique-activation theorem and the intended fail-closed policy has to be explicitly stated.

A single pre-signed fixed-output cancellation package then need not be re-signed merely because a later claim a* was selected. Any valid challenge for a* should open that SAME package. This does NOT instantiate the indispensable hash-only Build/Open secret-escrow functionality. Once a gate exists, native signature and graph binding must be audited before irreversible funding. A root commitment is not a key generator.

## Planned bounded adversarial tests

- distinguish a signed but unanchored fake activation from an anchored one;
- reject a valid old-epoch activation after a reset to a new outpoint;
- reject activation in an unrelated vault/outpoint and relabeled chain root;
- verify that three OR grounds correspond to one cancellation on same fixed outpoint;
- test forked BTC histories with two simultaneously qualifying activations, and record that uniqueness premise fails rather than claiming one global canonical spend;
- check a source claim with no proof of burn still requires a finite authenticated challenge-2 witness, not missing data alone.
