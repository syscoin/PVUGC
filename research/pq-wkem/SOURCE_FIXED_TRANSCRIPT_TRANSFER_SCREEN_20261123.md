## Construction attempt and exact transfer equation

Let S be a hash-commitment-based two-challenge proof for R(x_W,w); let N be one for the native relation V(vk,M,s)=1 AND H_bind(s)=d, where d=H_bind(sigma_cancel), with context included in H_bind. The digest is only for this candidate's exact-output test, not an assertion that it is safe under the full native auxiliary distribution. Both protocols have first message a, challenge bit e, response z, verifier V_P(a,e,z), and a deterministic extractor Ext_P(a,z_0,z_1). Assume for the screen that two valid responses with opposite challenge bits imply extraction of a full witness, except commitment binding failure. A valid alternative native witness is not by itself exact-byte recovery; second-preimage resistance for d with this auxiliary distribution would also be required. No native primitive or deployed endpoint is asserted here.

In the ordinary OR composition, publish a_S,a_N and a response (e_S,e_N,z_S,z_N) with e_S XOR e_N=c. Build knows sigma_cancel, hence can form the real N transcript, and simulate the S side for a chosen challenge. The public OR transcript is not claimed to hide anything without an actual simulator; the target is to add a transfer token T enabling an original witness to compute:

    Transfer(T,w,a_S,a_N,c,e_S,e_N,z_S,z_N)
        -> (1-e_S, 1-e_N, z'_S, z'_N)

with BOTH checks valid on the unchanged a_S,a_N. The XOR constraint stays c. ExtractNative then applies Ext_N to z_N,z'_N (ordered by challenge) and checks the digest and native message. Ext_S similarly extracts an actual source witness from z_S,z'_S. If valid opposite-challenge response pairs were produced, these extractors would be straight-line on classical output bytes, not quantum rewinding or a demanded disclosure of adversary internals. This is an attractive binding mechanism only if Transfer is actually implemented and native output recovery cannot bypass it. It is not a theorem that any adversary recovering the raw native signature must output such a pair.

The alternate choice of changing the total challenge c does not resolve the coupling: changing only e_S produces a new valid OR proof with unchanged e_N, so it supplies no second native response. Changing only e_N requires the missing native response directly. Keeping c fixed forces both bits to change; the XOR equation alone does not generate either response. Giving an oracle for native opposite-challenge responses is not permitted.

## Concrete binding-commitment instantiation screen

To expose which data are actually needed, consider the familiar graph-cycle proof in detail. For a graph G on m vertices, commit separately to every bit of the adjacency matrix A of a permuted copy pi(G), using independent lambda-bit salts r_ij:

    a_ij = H_com(domain || i || j || A_ij || r_ij).

Challenge 0 opens all cells and supplies pi; verify the permuted adjacency matrix. Challenge 1 gives a cycle visiting every vertex exactly once and opens its edge cells to 1; verify those openings. Two valid answers to the same commitments determine a cycle in G using the inverse permutation, unless some cell has two different openings (a collision in the domain-separated commitment). This extractor works on the *two answers*, with no private proof state. A reduction from an actual source verifier to such a graph would also have to preserve full original witness decoding, not merely satisfiability; for the native side it would have to preserve native witness decoding. Neither such compiler nor its resource use is claimed implemented.

There is a useful witness-transfer asymmetry. Fix a graph commitment with a valid challenge-0 answer. Publishing that answer gives pi and all salts, so any cycle in the original graph can be mapped by pi and its committed edges opened. Thus an arbitrary cycle witness can generate challenge 1 of this *same* first message. This is a constructive source-side transfer equation with no need to predict a future cycle. It also publishes the entire permuted graph and every salt; the challenge-1 proof does not contain a hidden setup value that becomes available just because it verifies. It is not the required joint native transfer.

In the opposite direction, if only challenge 1 is published, the unopened cells and the hidden permutation are not supplied by an unrelated witness. A cycle in G may differ from the fixed committed cycle under pi; its existence does not furnish the committed salts or that permutation. A simulated challenge-1 answer need not have any challenge-0 answer at all (the simulator can commit to an arbitrary matrix with the chosen cycle). Hiding the simulation randomness is not a transfer algorithm.

Now instantiate both S and N using this format, and try coupling via the OR challenge bits.

* If S starts at challenge 0 and its full openings are public, any original source cycle yields its challenge-1 response. If N starts at challenge 0, producing N's challenge-1 response requires a cycle of the native graph, i.e. the very native witness (after decoding). Source openings are not native openings and have no mathematical dependency on a native cycle.
* If N starts at challenge 1, its already-published native cycle uses permuted vertex indices. The missing N challenge-0 response includes the native permutation and all remaining salts. Reusing S's now-public full permutation as N's permutation does not help: in that case the native cycle already published in N decodes directly, with no source certificate. This is a direct full-public bypass, not a guess about a QPT extractor.
* If S starts at challenge 1, opening all cells to a permuted copy of its original graph may be impossible if S was simulated. Even with a genuine S first message, a future original witness does not reveal its fixed hidden permutation or unopened salts. The every-witness correctness condition is already absent.

A source-dependent native permutation coupling, for example pi_N = Map(T,cycle_S), is a real mathematical change from sharing the public permutations. It avoids the particular direct permutation reuse above only if Map returns the hidden *fixed* pi_N for all qualifying original cycles without exposing it otherwise. But no such public Map follows from cell binding: binding only limits answers for a chosen cell, it does not compute an opening or a permutation. Putting Map's result behind an ordinary proof verification is precisely a release bypass. Independent per-cycle hash masks would require unknown future cycle values in Build and repeat the full-prefix matching problem screened in the preceding note. Do not implement that variant.

## Disposition and next equation

The first-message binding approach provides a precise possible architecture for global consistency: if a public transfer object produced both opposite-challenge transcripts, an extractor could decode original evidence and the native capability from the same fixed commitments without inspecting secret intermediate wire labels. Its failure in this iteration is that ordinary OR challenge reallocation provides no coupling of the missing native response to a valid source response. The concrete commitment protocol permits witness transfer only in the direction where the relevant opening material is already public. Independent S and N transcripts, or shared public permutation material, do not implement the required correlated transfer. Neither hiding the permutation nor an ideal proof verifier generates it.

A later candidate would need an explicit classical-PPT correlated-first-message compiler that can serialize T and generate the native opposite response from ANY original certificate, with a jointly simulated full public distribution and arbitrary raw native recovery/forgery reduction. In particular, even success of special soundness for two valid responses would not establish the necessary reduction from arbitrary raw sigma recovery to production of those responses. Do not confuse that representation-dependent extractor with full-public security. Do not continue by increasing the number of OR challenges, salts, graph vertices, or repetitions: those leave the missing transfer equation unchanged.

This is an analytic construction screen, not a source compiler, test run, QROM proof, complete Build/Open or native signature. No empirical check was required after the missing equation was identified, and no tool-generated test counts are claimed. No ordinary PR comment or user notification is warranted. All prior original-source, multi-capsule, malicious-setup and native endpoint obligations remain in force.
