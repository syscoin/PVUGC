## Exact Boolean decomposition

For n-bit A and b, write P_i(A,b) := (b[0:i]=A[0:i]) AND (b[i] != A[i]), indexing bits from the most significant bit, i=0..n-1. Let i(A,b)=min{j:A[j]!=b[j]}.

**Lemma:** b != A iff exactly one P_i(A,b) is true. Indeed choose the first differing bit. No earlier bit can differ, and no later class can have all preceding bits equal. Thus

    R_inc(x_W,w) = OR_{i=0}^{255} (AdmitOriginal(x_W,w) AND P_i(A,Hash(Ancestor(w,h_rel)))).

This is an exact O(256) partition of the inequality portion, not a public compiler for AdmitOriginal, and it does not assume every class contains a real admitted history. Each class has 2^(255-i) string members (256-bit case); fake class strings exist cheaply. Source maturity, full Bitcoin ancestry and relevance are separate. No winning Syscoin branch or greater Syscoin cumulative work is introduced.

## Attempted classical PPT Build/Open: FIRST-DIFF-256

For illustration take a 256-bit cancellation secret S or a KDF seed used to unmask a frozen larger native signature. Builder draws 256-bit K, computes E=S XOR K. For each i computes pad_i=SHA256("R256-PREFIX"||A||uint16_be(i)) and t_i=K XOR pad_i. Publish C=(x_W,VK,E,{t_i},manifest). Honest Open verifies the full original R_inc on w, selects its unique class i, and returns E XOR t_i XOR pad_i = S. Hence *the displayed algebra* gives the same S for every qualified original witness; no witness canonicalization. It does not implement source verification or real native signing.

**Joint full-public attack:** Any classical adversary, even for a FALSE original instance, chooses i=0, obtains K=t_0 XOR SHA256("R256-PREFIX"||A||uint16_be(0)) and therefore S=E XOR K, without any header, PoW, witness or original certificate. It can also do this for each of the other 255 tokens. An honest VerifyOriginal(w) before decryption does not hide the raw public algebra. This is simultaneously a FALSE security violation and a hard-TRUE unauthorized-recovery violation, and also invalidates any blanket QPT-security claim (the attack is classical).

## Concrete repairs and the exact unsolved step

1. Replace pad_i with SHA256("source"||SHA256d(actual_parent_header(w))) or a hash of the actual complete header. Then a single frozen t_i would need the same pad for every independent future qualifying parent in class i. SHA-specific future headers do not share that digest; an explicit paired-synthetic-header check below demonstrates the nonconvergence. Original Bitcoin/auxpow admission was NOT simulated, so the result is not a statement about the observed distribution of real qualified source headers.
2. Hash-commit or Merkle-commit t_i instead of publishing it: source evidence identifies i but does not supply the secret preimage t_i. Publishing t_i or its opening for anyone to use revives raw recovery. Precomputing source-dependent openings for unknown future original witnesses requires the missing compact original-source cryptographic release mechanism; a commitment authenticates bytes, not their disclosure.
3. Seed pad_i by a secret builder seed or GGM private prefix: ordinary future witnesses have no way to obtain this independent private seed. Publishing the seed or child key again makes class i universally openable without a source certificate. Genuine SHA/AuxPoW data has no stipulated preexisting hidden secret shared by all valid class-i parents.

Thus the exact remaining equation is not the public first-differing-bit test. A practical cryptographic primitive must supply a **class-specific source-enforced hidden token** L_i(C,w), computable for *every* ORIGINAL qualified witness but unobtainable by public fabricated hash/class bytes, and produce one frozen S from all witnesses. A public software condition is not such enforcement. For any proposed new primitive, require a joint public-view QPT simulator/extractor handling native VK/capsule correlations, false instances, unauthorized hard-TRUE key recovery and forgery, adaptive malicious source coins, sibling selective openings, malicious N-of-N setup, abort/erasure, timing and Bitcoin censorship.
