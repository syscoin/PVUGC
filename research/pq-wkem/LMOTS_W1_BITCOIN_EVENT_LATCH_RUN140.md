## 1. A deterministic release property inside LMOTS_SHA256_N32_W1

RFC 8554 defines `LMOTS_SHA256_N32_W1` with `n=32`, `w=1`, `p=265` and
`ls=7`. There are 256 one-bit message-digest coefficients and 9 one-bit
checksum coefficients. NIST SP 800-208 lists this parameter set among its
approved SHA-256 LM-OTS parameter sets.

For a signature, RFC 8554 computes a 256-bit message digest `Q` and

`z = sum_i (1 - bit_i(Q))`, so `0 <= z <= 256`,

then encodes the checksum as `z << 7` in 16 bits. For `w=1`, the nine used
checksum coefficients are exactly the 9-bit binary representation of `z`.

The signature element at chain `i` is the private value `x[i]` hashed
`a_i` times. Thus `a_i=0` reveals raw `x[i]`, while `a_i=1` reveals the
one-step endpoint.

Take checksum-chain indices 256 and 257.

* If `z<=255`, checksum bit 8 is zero, so chain 256 reveals `x[256]`.
* If `z=256`, the checksum bits are `100000000`, so chain 257 reveals
  `x[257]`.

Therefore **every valid W1 signature reveals at least one of the fixed pair
`{x[256],x[257]}`**, independent of the signed message and the LM-OTS
randomizer. No probability or hardness assumption is used.

No single fixed checksum position has that property: every checksum bit is
one for some `z` in `[0,256]`. The two-chain fixed set is minimal for this
checksum argument.

The checker exhausts all 257 checksum values.

## 2. Bitcoin can check the revealed secret with OP_SHA256 and no CAT

For `w=1`, RFC 8554's first and only chain step is

`Y_i = SHA256(I || u32(q) || u16(i) || u8(0) || x[i])`.

When a source signature reveals raw `x[i]`, the spender constructs the
complete 55-byte string

`P_i = I || u32(q) || u16(i) || 0x00 || x[i]`

off chain. Existing Bitcoin `OP_SHA256` hashes the whole item directly.
No dynamic concatenation inside Script is needed.

A standard P2WSH latch is:

```
OP_SHA256 <Y_257> OP_EQUAL
OP_SWAP
OP_SHA256 <Y_256> OP_EQUAL
OP_BOOLOR OP_VERIFY
<PK_owner> OP_CHECKSIG
```

Initial stack, bottom to top:

`[owner_signature, candidate_256, candidate_257]`.

After a valid source signature, the owner places the 55-byte first-step
preimage for whichever selected coefficient is zero in the corresponding
candidate slot, leaves the other slot empty, chooses arbitrary Bitcoin
outputs, signs that transaction normally, and spends the whole segregated
UTXO.

The source release value is public after the event, but it is not a bearer
Bitcoin credential: a third party still lacks the owner's transaction
signature.

The exact script generated by the checker is 108 bytes with 8 non-push
opcodes. It uses three P2WSH witness arguments; the release item is 55 bytes.
With a 73-byte ECDSA signature, one real release item and one empty dummy,
the witness serialization is 241 bytes. These are far inside current P2WSH
policy/consensus bounds audited in Run 136.

BIP141 defines deployed P2WSH as SHA256 commitment to the witnessScript and
execution on the remaining witness stack. BIP143 supplies the SegWit-v0
CHECKSIG digest semantics.

## 3. Authenticating the selected source endpoints before funding

Standard RFC 8554 compresses the 265 W1 chain endpoints into

`K = SHA256(I || u32(q) || D_PBLC || Y_0 || ... || Y_264)`.

So a Bitcoin funder must not accept arbitrary `Y_256,Y_257` supplied by a
constructor.

One method requiring no change to the LM-OTS verification algorithm is to
publish an **expanded slot manifest** before funding:

1. all 265 chain endpoints (`265*32 = 8480` bytes);
2. the normal LMS authentication path for leaf `q`.

The funding client recomputes `K`, then the LMS leaf and Merkle root, and
requires equality with the already trusted source LMS public root. Only then
does it construct the Bitcoin script containing `Y_256,Y_257`.

The checker builds an RFC-shaped SHA256 LMS tree at height 5, recomputes K
from the 8480-byte expanded endpoint manifest, builds the authentication path
and verifies the root.

Publishing the expanded endpoint vector is extra public information beyond
the compact RFC 8554 public key. This run does **not** claim the standard
LM-OTS unforgeability theorem automatically covers that stronger public view.
For the Bitcoin latch, the selected objects are two domain-separated SHA256
images; an exact source-signature security audit under expanded-endpoint
disclosure remains required.

## 4. The designated one-time slot must be known before Bitcoin funding

The LMS/LM-OTS leaf index `q` is stateful and one-time.

For this adapter the designated q must be fixed before Bitcoin funding and
must not be consumed by an unrelated earlier signature. Any W1 signature
using the designated leaf releases one of the two Bitcoin-opening secrets.

Thus an ordinary sequential "whatever leaf is next later" interface is not
enough. The source design needs a reserved/predictable event slot or an
equivalent authenticated pre-event endpoint manifest.

This is directly relevant to source systems that already organize finality
signatures by one-time slots; it is not automatic for every LMS deployment.

## 5. Trust boundary

This construction removes the **Bitcoin-side** WE/MPC/covenant requirement
only if the source signature is already the event whose authority the bridge
accepts.

The source signing secret holders know the underlying one-time secrets before
the event. A malicious authorized source signer or sufficient signing
coalition can disclose a release secret early. Early-unlock security therefore
inherits the source consensus/signing assumption.

There is no extra bridge release committee in the construction, but the
ordinary source signer remains online and security-relevant. This is why the
result is not a solution to the generic offline WKEM stopping condition.

## 6. Why this matters after Runs 136–139

The earlier unchanged-Bitcoin branches left three generic difficulties:
direct P2WSH is tiny for generic circuits; a freshly sampled SHA256 target
has no source correlation in the clean QROM; and a native Schnorr wrapper
still needs a precommitted event-gated scalar.

This result supplies the precise external-correlation escape left open by the
hashlock barrier:

**an ordinary hash-based source certificate can itself reveal the precommitted
Bitcoin hashlock secret.**

No generic witness-to-random-preimage compiler is needed in that source-specific
case.

The next practical audit is exact and falsifiable: determine whether the real
source finality-signature system has a predictable one-time slot whose
authenticated public chain endpoints can be exposed before Bitcoin funding and
whose normal valid certificate necessarily releases one of them only at the
intended event. If not, discard this branch rather than assuming such a slot.

The generic-NP public/offline PQ WKEM stopping condition remains NOT MET.
