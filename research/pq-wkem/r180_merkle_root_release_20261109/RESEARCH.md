## Attempted new release architecture: a hash-root as native key

A fixed N-of-N preauthorized Bitcoin challenge path commits native verification keys before funding. Could an SLH-like hash authentication root be chosen so future qualified source-fork evidence becomes a valid native signing path under that *same frozen root*, eliminating witness encryption? A fixed toy Merkle root R commits a source baseline child identity A at semantic height/slot i. A future challenger supplies a different qualified child identity B and an authentication path; the hypothetical Open would use its path as an input to form the frozen cancellation authorization. This is a candidate interface, NOT an implemented native signature compiler.

**Exact binding lemma.** Fix collision-resistant, domain-separated H_leaf(index,value) and H_node(left,right), and a Merkle root R. Given ANY TWO accepted, classical fixed-depth openings `Verify(R,i,A,p)=Verify(R,i,B,p')=1` with `A != B` at the SAME index i, a deterministic polynomial-time, straight-line extractor produces an explicit hash collision. If leaf hashes are equal, distinct leaf encodings collide. Otherwise the two digest paths start different and end at the same R. At the first level of equality, the prior digests differ, so the two ordered parent inputs differ but hash to the same digest. This is valid for outputs of an arbitrary QPT adversary (nonuniform advice allowed); resistance requires an **independent quantum collision-resistance assumption**, not classical-to-quantum lifting. It does not show that an adversary recovering a native signature necessarily outputs two Merkle openings.

Therefore ordinary fixed-root Merkle membership cannot add a previously unknown **different** Syscoin child at the same semantic slot while keeping R unchanged, absent a hash collision. A new root R_B can bind B, but that is a NEW native verification target. Bitcoin's preauthorized key does not automatically follow an updated root.

## Exact repairs considered

- **Dynamic source Merkle root:** appending B into a formerly empty slot or replacing A at the same slot changes R. A pre-signed transaction fixed to old native VK cannot accept new R without another authorized key/update procedure. No trusted online authority or Bitcoin verifier opcode is supplied.
- **Wildcard or empty slot:** the old proof does not open arbitrary future B. A public universal wildcard would admit forged, unqualified source values. A secret trapdoor to replace committed values changes the primitive and creates retention/setup risks.
- **Distinguish work certificates:** do NOT put parent WorkID in semantic Merkle leaves. Two Bitcoin parent work certificates can commit to the same Syscoin child. Correct normalization keeps the pure child OutcomeID; source authentication still requires full AuxPoW/BTC evidence, not merely the normalized hash.
- **Commit verifier code instead:** a hash of source-validation code is a commitment to code bytes. Native hash-signature verification does not execute that off-chain verifier. An off-chain `if valid then reveal public secret` is bypassable, returning to the missing witness-dependent cryptographic gate.
- **Future witness hash-chain:** known source ancestor hashes are public and not secret release preimages. Real child/parent commitments do not yield one hidden precommitted value from every possible future valid fork.
