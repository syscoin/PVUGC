## Candidate: public first-difference SHA release
Let b be a fixed 256-bit source semantic ancestor hash and sigma the frozen native cancellation signature. For i in [0,255], choose a public label L_i computed from public anchor, i and the opposite bit (1-b_i), and publish E_i = sigma XOR SHA256(domain-pad,L_i). If alternate semantic v differs from b in any bit i, direct computation E_i XOR SHA256(domain-pad,L_i) returns the SAME sigma, independently of v. Only 256 rows are needed for this semantic correctness claim. This is a hash-only public carrier, not yet a candidate for secure original release.

It fails completely: the label is public, so the raw release works for an attacker-supplied v even when v has no authenticated AuxPoW parent coinbase, valid source header history, root qualification or relevance to the withdrawal. A verifier check performed AFTER reading the raw pad cannot block the output. The published reproducer checks all 255 semantic alternatives in an 8-bit toy and all 255 fake alternatives, showing identical early recovery. No claim that those fake values are genuine source witnesses is made.

Scoped factorization lemma: If public Open(C,w) factors as a publicly callable G(C,nu(w)), and there is an efficiently constructible s* in the image nu(W_valid) of at least one ORIGINAL qualifying witness for which correct opening equals sigma, an attacker computes G(C,s*) directly without producing that witness. This applies to arbitrary nonlinear G, not only XOR, but only under the stated constructible-image hypothesis. It does NOT prove generic hash-WE impossible; the 8-bit experiment intentionally models an overbroad semantic-only predicate, not actual work/certification.

## Exact attempted repairs
(A) Setup-private labels s_i prevent fabricated semantic values from opening, but complete independent future BTC/SYS evidence does not reveal s_i. An online party or miner-held Lamport label would be a different source relation, and miners may retain such labels before evidence exists. (B) Make each label a hash of actual future source transcript w. That adds source dependence but Build cannot precompute a pad aligned with EVERY future work certificate; one frozen E_i calibrated for w_A does not correctly open for distinct qualifying w_B. (C) Use a common known PoW zero prefix. The prefix is syntactically constructible without mining and therefore opens early.

## Deeper two-root Merkle-path attempt
Replace source-bit labels with the full ordered SHA-Merkle path from actual source coinbase/child history. This path commits to a specific source root. In a real fork, two branches ordinarily yield DIFFERENT roots R_A and R_B; they are NOT contradictory openings to the SAME root. The synthetic checker shows paths to two different roots, each locally valid only to its own root. A pad frozen under the available path p_A will not decode using arbitrary later p_B; a pad depending only on the common known anchor is public and leaks early.

Exact Merkle soundness distinction: For canonical domain-separated hash tree, two distinct leaves at the SAME position each verifying to one fixed root would yield a leaf-hash or internal-node hash collision. An ordinary fork with distinct roots yields no such collision. The checker is synthetic; it does not validate a real Bitcoin AuxPoW link or assert a SHA collision. Different parent-work wrappers for the SAME Syscoin child remain the same semantic child, not a fork.

The source Merkle path is a plausible authenticated-evidence INPUT, but it does not independently give setup-compatible secret labels for all future roots. A root commitment authenticates bytes, not a hidden release pad; a public Merkle verifier is not a cryptographic gate.
