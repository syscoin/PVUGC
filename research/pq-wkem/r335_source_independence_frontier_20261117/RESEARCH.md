## Why R333/R334 should not lead to another source-issuer variant
The next attempt considered whether honest independent source history could supply a setup-chosen shared secret merely through additional *unpredictable* SHA/AuxPoW bytes, without a public nontrivial source-gated program. Separate `source supplies entropy` from `a qualifying source witness enables a hard computation`. These are not interchangeable.

Let Z collect all published instance, capsule, claim, native VK/message, authenticated baseline, and allowed auxiliary context. Builder chooses a hidden cancel pad K and public capsule C (C included in Z); the future original source process outputs a certificate W. In the honest-independent-source submodel, any mining strategy may depend on ALL of Z, but has no unrevealed setup randomness or retained shared key: its conditional distribution is Q(W|Z). Then
  Pr[K=k,W=w|Z=z] = Pr[K=k|Z=z] Q(w|z),
so **I(K;W | Z)=0** exactly. This also permits an adaptive miner to choose certificates based on public C. It does NOT cover malicious collusion in which the source process retained unrevealed builder/source-issued secrets.

If public Open(Z,W) outputs K with average error <= epsilon over this distribution, Fano's bound gives
  H(K|Z,W) <= h2(epsilon) + epsilon * log2(|Kspace|-1).
By conditional independence, H(K|Z,W)=H(K|Z), so for exact opening H(K|Z)=0. The capsule already MATHEMATICALLY determines the key. This is **not a computational break**: an efficiently obtainable valid W may still be needed to COMPUTE the key in polynomial time. Ordinary witness encryption can have exactly this information-theoretic structure. Therefore **absence of a setup-correlated secret in Bitcoin/Syscoin certificates does not prove hash-only WE impossible**; it rules out treating ordinary source entropy as an automatically usable setup-chosen receipt.

Conversely, treating the actual ORIGINAL certificate as a *computational witness* could in principle be useful; whether a serializable hash-only public gate can exploit it is the unresolved construction. A claim that two independently mined SHA values automatically reconstruct a frozen builder-chosen pad is unsupported by this model.

## Constructive repair attempted: two-suffix maturity frontier
For claim-prefix branch 3, write a source certificate as W=(p,d), where p is a miner-retainable conflicting child/parent PREFIX and d is the as-yet-unavailable authenticated suffix needed to satisfy exact LC maturity, relevant interval tags, anchors, windows and reset/deadline. A source-derived release key should obey TWO requirements simultaneously:
  (A) Open(C,p,d0)=Open(C,p,d1)=K for ANY two independently qualified and relevant ORIGINAL completions d0,d1, even with different parent coins/child histories;
  (B) from C and a prematurely retained p ALONE, or invalid/spliced d, arbitrary QPT attackers must not recover K except by producing an actual qualified ORIGINAL certificate or independently breaking the stated hash/native assumptions.
Analogous prefix/final-admission timing applies to strictly greater anchored BTC work. Branch 2 remains an independent finite, specifically authenticated burn-refutation predicate and is not silently promoted to a PoW/depth requirement.

A proposed purely hash-derived prefix pad `K_p=H(domain||claim||p)` breaks (B): the miner computes it before the suffix qualifies, regardless of a later plaintext verifier. Replacing it by `K_d=H(domain||claim||p||d)` changes the value under two distinct qualifying d and breaks (A), unless a nontrivial correction function is furnished. A setup-fixed public SHA checksum, target-prefix constant, or common baseline ancestor cannot provide a **hidden** K; a future certificate's ordinary SHA fields do not carry a chosen hidden coefficient. A public correction callable on fabricated p/d is not a source gate, and a privately evaluated correction is not a public serializable Build/Open. This rejects these particular prefix/suffix pad placements analytically; it is NOT a generic impossibility theorem for computational WE or a statistical claim about concrete SHA outputs.

The **specific positive direction** retained is therefore not a new random-pad/slope/label issuer: construct a public polynomial-time **computational access mechanism** for the whole ORIGINAL verifier that uses W as a hard-to-obtain computation resource while keeping every-witness output equal to setup-frozen K. It must enforce global input consistency inside release, not via an optional post-check, and support all three OR grounds. Do not count a named `SourceGate` or ideal evaluation oracle as its implementation. This run does **not** instantiate that mechanism or a joint public QPT simulator.
