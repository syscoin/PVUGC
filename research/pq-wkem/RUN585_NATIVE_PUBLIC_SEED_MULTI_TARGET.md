## Concrete FIPS 205 key interface
NIST FIPS 205 algorithms 18–20 define `PK=(PK.seed,PK.root)`, `PK.root=xmss_node(SK.seed,0,h',PK.seed,ADRS)`, and private `SK=(SK.seed,SK.prf,PK.seed,PK.root)`. The public root is independent of `SK.prf`. Anyone recovering **any** `SK.seed` matching the public root under the specified public `PK.seed` can choose a new `SK.prf` and compute a signature that passes the native verifier: `SK.prf` selects the message randomizer R, which is transmitted in the signature, not authenticated as the original secret key. This is an algebraic observation about verification, not a known practical attack or a challenge to NIST compliance. For 128s/f, 192s/f, 256s/f, `SK.seed` has 128, 192, 256 bits, respectively. NIST requires independently fresh `PK.seed` for each key.

## Theorem — distinguish two native public-key confirmation oracles
Let `S={0,1}^k`, `|S|=M`. Honest setup and release are classical PPT. An arbitrary quantum attacker sees the complete public checking keys and can coherently execute public functions; its quantum advice can only help the **attack upper bound**. Fix N distinct honestly chosen secrets `s_i`.

**World A, shared unsalted function:** Public injective F is the same for every claim, and targets are `y_i=F(s_i)`. Coherently test `Q(s)=[F(s) in {y_i}]` using **one F evaluation and a reversible lookup**. Exactly N/M of secrets match. Grover/BBHT finds a signing seed for some claim in `O(sqrt(M/N))` F evaluations. In noninjective real-world maps, the planted seeds still match; additional matches can only make this attack easier. An upstream `KDF(context_i,K_i)` changes the planted seeds but not this shared final-key membership predicate.

**World B, independently publicly seeded function family:** Each claim uses a distinct independently sampled ideal permutation `F_i`, `y_i=F_i(s_i)`. A coherent **indexed** oracle takes `(i,s)` and returns `F_i(s)`. The direct matching predicate has exactly N accepted pairs in an `N M` pair domain, density **1/M**, not N/M. Unstructured quantum search for any pair takes `Theta(sqrt(M))` indexed-function oracle queries under this *ideal independent-permutation model*. This lower bound is not established for actual FIPS-205 XMSS roots, public program encodings, or correlated secret advice. Evaluating all N different `F_i(s)` for a common candidate s is **not** one indexed root query; a parallel quantum machine can trade width/depth but not freely eliminate work.

These are different security games. Reusing a common `PK.seed` across many SLH roots creates the shared-function shape and drops its structural per-key separation; FIPS 205 requires fresh independent public seeds. Merely salting the upstream witness-release KDF does not achieve this separation if the *native* signing seed is still checked by the same public function.

## Exact root-query accounting, not quantum hardware security
For N=2^a target keys and k candidate signing-tree seed bits, World A's nominal quantum-root-evaluation exponent is `(k-a)/2`; World's B ideal indexed oracle exponent is `k/2`. Thus k=128,N=1 gives 2^64 queries in either game; k=128,N=2^20 gives 2^54 in World A versus 2^64 in B; k=256,N=2^20 gives 2^118 in A versus 2^128 in B; k=276,N=2^20 gives 2^128 in A. For *128 raw root-query work* against this attack, World A needs `k>=256+log2 N`; World B's analogous ideal target needs `k>=256`. Root computations may be expensive, and NIST PQ security categories are not equivalent to raw Grover query exponents. These are upper bounds against one search method, **not** full security estimates or a claim that nominal SLH-DSA 128 is broken.

## Relation-dependent release and attack taxonomy
The public native-key search bypasses the local mixer and supplies no ORIGINAL witness. Successful recovery of any accepted native signer need not produce an accepted global source representation. Run 259 provides only the *subsequent* `complete accepted representation -> ORIGINAL witness`, not the missing `signature -> representation`. Gate-seam cancellation, global gauge alignment or fingerprinting are unnecessary; the chosen-input public verification oracle and multiple public claim keys are sufficient.
